# Лабораторна робота №8 — Публікація Dogfight у Production: Docker, Метрики, Надійність та PWA

Переведення багатокористувацької аркади **Dogfight** з локального середовища розробки у повноцінний production-режим: кероване завершення роботи за сигналом `SIGTERM`, перевірка `Origin` та ліміти з'єднань з однієї IP, структуровані JSON-логи через `pino`, живі метрики у форматах Prometheus та JSON, багатоетапний образ Docker (< 200 МБ), конвеєр безперервного розгортання за git-тегами, підтримка встановлення як PWA (разом із мобільним сенсорним керуванням) та оформлення README як сторінки готового продукту.

## Підтверджені рішення та конфігурація

> [!IMPORTANT]
> Усі ключові архітектурні рішення узгоджено під час першого етапу планування та покладено в основу реалізації.

- **Формат ендпоінта `/metrics` (Підтверджено)**: Ендпоінт експортує метрики у стандартному текстовому форматі Prometheus через `prom-client`, а при запиті з параметром `?format=json` або заголовком `Accept: application/json` повертає структурований JSON-знімок для зручного перегляду та дашборду.
- **Конвеєр CD за тегом `v*` (Підтверджено)**: GitHub Actions збирає багатоетапний Docker-образ з прокиданням `GIT_SHA`, публікує його в GitHub Container Registry (`ghcr.io`) та виконує універсальний крок деплою (Fly.io через `FLY_API_TOKEN` та/або Render через `RENDER_DEPLOY_HOOK_URL`).
- **Перевірка відмовостійкості та ізоляції (Підтверджено)**: Автоматизовані хаос-тести входять до основного набору тестів (`npm test`), а також виносяться в окремий виконуваний скрипт навантажувального та хаос-тестування для демонстрації на захисті.

## 1. Огляд та ключова концепція

- **Що робить система**: Забезпечує стабільну роботу авторитетного ігрового WebSocket-сервера та клієнта в інтернеті за протоколом `wss://` за зворотним проксі, дозволяючи гравцям з різних мереж грати в одній кімнаті з передбаченням руху, інтерполяцією та телеметрією в реальному часі.
- **Цільова аудиторія**: Гравці на десктопах і смартфонах (через встановлений PWA-додаток), а також інженери/екзаменатори, які перевіряють поведінку сервера під час зупинки контейнера, спам-атак і мережевих збоїв.
- **Ключова цінність**: Прозора спостережуваність (логи `pino` + метрики `prom-client`), захист від вичерпання ресурсів (ліміти на IP, кімнати, частоту пакетів, перевірка `Origin`), нульова втрата даних логів при перезапуску контейнера та миттєве автоматичне повернення гравців у лобі після перезавантаження сервера.

## 2. Досвід користувача та візуальний дизайн

- **Ключові користувацькі сценарії**:
  1. **Вхід та гра**: Гравець відкриває гру за публічним посиланням (`https://`), бачить у лобі статус підключення та версію збірки (`git SHA`), обирає або створює кімнату й одразу керує кораблем з клієнтським передбаченням.
  2. **Встановлення на телефон (PWA)**: У шапці лобі відображається кнопка встановлення додатка («Встановити гру»), яка викликає системний діалог встановлення в Chromium/Android або показує компактну інструкцію для iOS Safari. На сенсорних екранах з'являються зручні екранні кнопки керування (тяга, поворот, вогонь) з розміром натискання не менше `44x44px`.
  3. **Плавне перепідключення при зупинці сервера**: Коли сервер отримує `SIGTERM`, він надсилає активним клієнтам повідомлення `shutdown` і закриває WebSocket з кодом `1001`. Клієнт автоматично повертає гравця у стан лобі зі зрозумілим повідомленням статусу й за експоненційною затримкою відновлює зв'язок, щойно сервер знову стає готовим.
- **Візуальна ідентичність та тема**:
  - *Естетичний напрям*: Тактичний ретро-футуристичний радарний інтерфейс (глибокий темний фон космосу, контрастна векторна графіка кораблів та астероїдів, чітка телеметрія Netgraph).
  - *Кольорова палітра (60-30-10)*:
    - `60%` Домінантне полотно: темний графітовий космос (`#101414` та `#111111` на ігровому полотні).
    - `30%` Структурні поверхні: панелі керування та лобі (`#1b2424`, `#151c1c`) з тонкими контурами (`#52665d`).
    - `10%` Акценти дії та станів: радарний зелений (`#a7ff83`) для активної телеметрії та здоров'я, бурштиновий (`#ffd54f`) для снарядів і червоний (`#f44336`) для критичних попереджень.
  - *Типографіка та ієрархія*: Системний геометричний гротеск для інтерфейсу лобі у парі з моноширинним шрифтом (`monospace`, `tabular-nums`) для Netgraph, RTT, FPS, лічильників трафіку та штампа версії `git SHA`.
- **Інтерактивний зворотний зв'язок**: Миттєвий відгук елементів керування (`<= 150 мс`), індикатор мережевого статусу (Онлайн / Перепідключення / Офлайн-режим PWA) та жива панель серверних метрик у лобі.

## 3. Ключові продуктові рішення та компроміси

- **Рішення 1: Один процес (Single Instance) із задокументованою межею ємності**
  - *Обраний підхід*: Усі гравці однієї кімнати обслуговуються в пам'яті одного процесу Node.js; масштабування на кілька інстансів через Sticky Sessions та Redis Pub/Sub детально описано в архітектурному розділі README.
  - *Чому*: Авторитетна фізична симуляція на частоті 30 Гц вимагає мілісекундного доступу до стану сутностей без серіалізації між процесами на кожному кроці; один процес легко витримує сотні одночасних гравців при використанні бінарного протоколу `DataView`.
- **Рішення 2: Структуроване логування `pino` у стандартний потік виводу (`stdout`)**
  - *Обраний підхід*: Усі події життєвого циклу (`server.started`, `room.created`, `player.joined`, `ws.rejected`, `server.shutdown`, `uncaughtException`) записуються як NDJSON-рядки через `pino` з полями `roomId` та `playerId` без чутливих даних.
  - *Чому*: Контейнерні платформи збирають логи зі `stdout`, а `pino` мінімізує навантаження на головний потік Event Loop, не затримуючи 30 Гц ігровий цикл.
- **Рішення 3: Подвійний формат `/metrics` (Prometheus + JSON) та моніторинг Event Loop Utilization**
  - *Обраний підхід*: Використання `prom-client` разом із `perf_hooks.monitorEventLoopDelay` та `performance.eventLoopUtilization()` для точного вимірювання p99 тривалості тіка та завантаженості циклу подій.
  - *Чому*: Дозволяє підключати стандартний стек Prometheus/Grafana і водночас читати метрики безпосередньо з браузера чи тестів у форматі JSON.

### Модель даних, конфігурація та метрики

1. **Валідація конфігурації (Zod)**:
   - `PORT`, `HOST` (`0.0.0.0` за замовчуванням), `NODE_ENV`, `LOG_LEVEL` (`info`, `debug`, `warn`, `error`, `silent`), `GIT_SHA` (або `COMMIT_SHA`).
   - `ALLOWED_ORIGINS` (список дозволених доменів через кому; підтримує точний збіг та безпечну роботу з локальним хостом у режимі розробки).
   - `MAX_CONNECTIONS_PER_IP` (ліміт одночасних WebSocket-з'єднань з однієї IP-адреси, з урахуванням `X-Forwarded-For` за проксі).
   - `MAX_ROOMS`, `MAX_PLAYERS_PER_ROOM`, `MAX_PAYLOAD_BYTES`, `RATE_LIMIT_PER_SEC`, `INPUT_RATE_LIMIT_PER_SEC`, `MAX_BUFFERED_AMOUNT`, `JOIN_TIMEOUT_MS`, `HEARTBEAT_INTERVAL_MS`.
2. **Ендпоінти життєвого циклу та спостережуваності**:
   - `GET /health`: Повертає `200 OK` з `{ status: "ok", version, gitSha, uptime, eventLoopUtilization }`, поки процес живий.
   - `GET /ready`: Повертає `200 OK`, коли сервер готовий приймати гравців, або `503 Service Unavailable`, якщо розпочато планове завершення (`shuttingDown === true`) чи досягнуто глобальної межі кімнат.
   - `GET /metrics`: Експортує метрики:
     - `dogfight_connected_players` (Gauge) — активні гравці.
     - `dogfight_active_rooms` (Gauge) — активні кімнати.
     - `dogfight_messages_in_total` / `dogfight_messages_out_total` та похідні швидкості `messages/s` (Counter / Gauge).
     - `dogfight_bytes_in_total` / `dogfight_bytes_out_total` та `bytes/s` (Counter / Gauge).
     - `dogfight_tick_duration_ms` (Histogram / Summary з p99, avg, max по кімнатах).
     - `dogfight_event_loop_utilization` (Gauge) — коефіцієнт зайнятості циклу подій Node.js.
     - `dogfight_memory_rss_bytes` (Gauge) — використання пам'яті RSS.
     - `dogfight_ws_rejected_total{reason}` (Counter) — відхилені підключення та пакети за причиною (`origin`, `ip_limit`, `rate_limit`, `invalid_payload`, `room_limit`, `shutting_down`).
3. **Кероване завершення (`SIGTERM` / `SIGINT`) та обробка винятків**:
   - При отриманні `SIGTERM`:
     1. Прапорець `shuttingDown` переходить у `true` (`/ready` миттєво повертає `503`, нові WebSocket-рукостискання відхиляються).
     2. HTTP-сервер припиняє приймати нові з'єднання (`httpServer.close()`).
     3. Усім підключеним клієнтам надсилається повідомлення `{ v: 0, type: "shutdown", reason: "Server restarting" }` і викликається `socket.close(1001, "Server shutting down")`.
     4. Зупиняються ігрові цикли кімнат, дописуються та закриваються потокові NDJSON-логи матчів та буфери логера `pino`.
     5. Процес завершується з кодом `0` значно швидше за 10 секунд.
   - При `uncaughtException` та `unhandledRejection`: подія логується на рівні `fatal` разом зі стек-трейсом через `pino`, після чого процес негайно завершується з ненульовим кодом (`process.exit(1)`).
4. **Контейнеризація та CI/CD**:
   - Багатоетапний `Dockerfile` на базі `node:22-alpine`:
     - Етап 1 (`builder`): кешоване встановлення залежностей за `package*.json`, збірка клієнта Vite та компіляція TypeScript для `shared` і `server`.
     - Етап 2 (`runner`): чистий образ `node:22-alpine`, встановлення виключно production-залежностей (`npm ci --omit=dev`), копіювання скомпільованих артефактів, перемикання на непривілейованого користувача `USER node`, вбудований `HEALTHCHECK` до `/health` та запуск у exec-формі `CMD ["node", "server/dist/index.js"]`.
   - `docker-compose.yml` та `.dockerignore` для швидкої локальної перевірки образу (< 200 МБ) і тестування `docker stop`.
   - Оновлений workflow GitHub Actions, який на кожен push проганяє `typecheck`, `lint`, `test`, перевіряє збірку Docker-образу, а на теги `v*` публікує образ у GHCR і запускає деплой.
5. **Хаос-тестування (Chaos & Isolation Verification)**:
   - Сценарій 1 (Раптове зникнення клієнта): термінація сокета посеред матчу — сервер коректно очищує корабель і кулі гравця, оновлює список гравців у кімнаті.
   - Сценарій 2 (Вбивство/перезапуск сервера): сервер виконує graceful shutdown (`shutdown` + код `1001`) — клієнт переходить у стан очікування в лобі з повідомленням про перезапуск і автоматично відновлює роботу після підняття сервера.
   - Сценарій 3 (Флуд ~1000 битих кадрів/с): зловмисний клієнт у Кімнаті B надсилає потік пошкоджених пакетів — сервер миттєво відключає його з кодом помилки протоколу/ліміту, збільшує лічильник `dogfight_ws_rejected_total`, а час кроку (`tickDurationMs`) у сусідній Кімнаті A залишається стабільним без деградації.
