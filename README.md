# Lab 01: Event Loop and Game Loop

## Експеримент 1: Блокуючий цикл (while на 100мс)
* **Що бачить гравець:** Гра повністю зависає на час виконання циклу, екран не оновлюється, корабель завмирає. Показники `frames/s` падають.
* **Пояснення:** JavaScript виконується в одному потоці (Call Stack). Синхронний цикл `while` блокує цей потік. Event Loop забирає задачі з черг і дозволяє браузеру відмалювати кадр (Paint) лише тоді, коли Call Stack порожній[cite: 1]. Тому 100 мс синхронного блокування неможливо обійти — браузер просто чекає.

## Експеримент 2: setInterval замість requestAnimationFrame
* **Що бачить гравець:** Візуальні ривки (stuttering). `frames/s` починає "стрибати". Після згортання вкладки і повернення корабель може телепортуватися.
* **Пояснення:** `setInterval(fn, 16)` не синхронізований з частотою оновлення монітора (16 ≠ 16.667 мс). Крім того, таймери поводяться непередбачувано у фонових вкладках[cite: 1, 3]. Натомість `requestAnimationFrame` викликається браузером безпосередньо перед наступним малюванням кадру (paint), що забезпечує ідеальну плавність[cite: 1, 3].

## Експеримент 3: Змінний крок (dt) замість фіксованого
* **Що бачить гравець:** Траєкторія і швидкість корабля змінюються залежно від того, наскільки сильно завантажений процесор або яка частота екрана (60 Гц чи 120 Гц). 
* **Пояснення:** Якщо множити швидкість на реальний `dt` (змінний час між кадрами), симуляція стає недетермінованою. Це означає, що за однакових дій гравця результат на різних комп'ютерах буде різним, що є критичною помилкою для мультиплеєрних ігор. Фіксований крок (через `accumulator`) гарантує, що логіка завжди рахується рівно 60 разів на секунду[cite: 1, 3].
